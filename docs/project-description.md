# Stockio — описание проекта

## Назначение

Stockio — учебный сервис на Go, подключенный к преподавательской платформе через Kafka. Текущая версия проверяет базовый цикл обмена: регистрация сервиса, heartbeat, прием рыночных свечей и публикация рекомендаций `HOLD`.

Стратегия Momentum выбрана для будущей работы, но пока не реализована. Сервис не формирует `BUY` или `SELL`, не отправляет реальные торговые заявки и не подключается к бирже.

## Текущие возможности

- Загружает и проверяет конфигурацию из переменных окружения.
- Подключается к `omsu.7bits.it:9094` по `SASL_SSL` и `SCRAM-SHA-256`.
- Ждет назначения разделов `account.registration.result`, отправляет запрос регистрации и принимает только связанный с ним ответ `REGISTERED`.
- Публикует heartbeat примерно раз в 5 секунд.
- Читает события `market.candle.closed` из настроенного `CANDLE_TOPIC`.
- На каждую корректно прочитанную свечу публикует рекомендацию `HOLD` с данными исходной свечи и идентификаторами зарегистрированного сервиса.
- Предоставляет HTTP `GET /health` и корректно завершает HTTP-сервер по сигналу остановки.
- Собирается в Docker-образ; Compose передает контейнеру локальный `.env`.

Компонентная и контекстная схемы приведены в [диаграмме компонентов](diagrams/components.mmd) и [контекстной диаграмме](diagrams/context.puml).

## Границы системы

### Внутри Stockio

- запуск и сборка компонентов приложения;
- конфигурация и проверка обязательных параметров;
- сценарий регистрации, heartbeat и обработки свечей;
- модели Kafka-событий и интерфейсы для публикации/чтения;
- адаптер franz-go для Kafka;
- HTTP endpoint `/health`;
- структурированные журналы.

### Вне Stockio

- Kafka broker и его учетные записи;
- платформа, темы и обработка регистраций, heartbeat и рекомендаций;
- источник и расписание публикации свечей;
- настройка запусков, тем портфелей и начального капитала;
- хранение аккаунтов, портфелей, сделок и результатов на стороне платформы;
- реальная биржа и реальные торговые операции.

Для текущей реализации отдельная база данных не используется. Состояния обработанных свечей не сохраняются локально.

## Внешние участники

| Участник | Ответственность |
| --- | --- |
| Студент/разработчик | Заполняет `.env`, запускает сервис, выбирает выданные идентификаторы и тему свечей. |
| Преподаватель | Выдает Kafka-пару, учебную группу и согласует поток свечей. Настраивает платформенный запуск и тему портфеля. |
| Учебная платформа | Обрабатывает регистрацию, назначает настройки аккаунту и публикует/принимает события. |
| Kafka broker | Доставляет события через темы и разделы. |
| Stockio | Регистрируется, читает свечи и отправляет heartbeat и `HOLD` рекомендации. |

## Kafka и контракт событий

Для соединения используются:

- брокер `omsu.7bits.it:9094` (можно переопределить через `KAFKA_BROKERS`);
- `security.protocol=SASL_SSL`;
- `sasl.mechanism=SCRAM-SHA-256`;
- `KAFKA_USERNAME` — выданный ключ;
- `KAFKA_PASSWORD` — секрет пары;
- `ACCOUNT_SECRET_KEY` — тот же ключ, а не пароль. Это поле уходит в registration, heartbeat и recommendation payload.

`GROUP_ID` в событиях — учебная группа. `KAFKA_GROUP_ID` — техническая consumer group Kafka; для каждого студента требуется отдельное уникальное значение.

| Kafka topic | Направление | Тип события | Назначение |
| --- | --- | --- | --- |
| `account.registration.request` | Stockio → Kafka | `account.registration.request` | Запрос регистрации аккаунта и сервиса. |
| `account.registration.result` | Kafka → Stockio | `account.registration.result` | Подтверждение или отказ; Stockio связывает его с запросом по `causationId`. |
| `account.service.heartbeat` | Stockio → Kafka | `account.service.heartbeat` | Сигнал о работающем сервисе примерно раз в 5 секунд. |
| `CANDLE_TOPIC` | Kafka → Stockio | `market.candle.closed` | Закрытые свечи выбранного потока. |
| `strategy.recommendation.created` | Stockio → Kafka | `strategy.recommendation.created` | Одна рекомендация `HOLD` на обработанную свечу. |
| `strategy.recommendation.result` | Kafka → Stockio | `strategy.recommendation.result` | Результаты собственных рекомендаций; текущая версия читает их, но не использует для изменения логики. |

Названия служебных тем имеют значения по умолчанию в `internal/config/config.go`. Свечную тему необходимо согласовать с преподавателем. У платформенного портфеля есть собственная тема по умолчанию: изменение `CANDLE_TOPIC` в сервисе само по себе не меняет тему портфеля.

События используют JSON-конверт версии `1.0`: `eventId`, `eventType`, `schemaVersion`, `occurredAt`, `correlationId`, `causationId`, `producer` и `payload`. В регистрации указываются ключ, `accountId`, `accountName`, учебный `groupId`, `strategyId`, `strategyName` и `serviceName`. Пароль Kafka в JSON не отправляется.

### Последовательность регистрации и работы

1. Consumer запускает чтение настроенных тем и ждет назначения хотя бы одного раздела `account.registration.result` (максимум 30 секунд).
2. Stockio отправляет `account.registration.request`. Подтверждение доставки от Kafka означает только прием брокером, а не успешную регистрацию.
3. Сервис ждет ответ платформы до 30 секунд. Он принимает только ответ `REGISTERED`, у которого `causationId` совпадает с `eventId` запроса.
4. После регистрации запускается heartbeat.
5. На каждое событие `market.candle.closed` сервис формирует рекомендацию `HOLD`. В рекомендации сохраняются `runId`, `sequenceNumber`, тикер и идентификатор исходного события.

Идентификаторы аккаунта, стратегии и сервиса должны оставаться стабильными между запусками. Повторная регистрация того же аккаунта на стороне платформы обновляет его имя и группу; сервис не передает параметры портфеля.

## Конфигурация

Пример переменных находится в [`.env.example`](../.env.example). Обязательные значения: Kafka username/password, `KAFKA_GROUP_ID`, `CANDLE_TOPIC`, `ACCOUNT_SECRET_KEY`, `ACCOUNT_ID`, `ACCOUNT_NAME`, `GROUP_ID`, `STRATEGY_ID`, `STRATEGY_NAME` и `SERVICE_NAME`. Брокер и HTTP-порт имеют значения по умолчанию.

`.env` содержит локальные учетные данные и не должен попадать в Git или Docker build context. В репозитории хранится только шаблон без настоящих ключей и паролей.

Consumer использует `earliest`, если для группы нет сохраненной позиции. Автокоммит выключен, и приложение не коммитит обработанные offsets. Поэтому после перезапуска события могут быть прочитаны повторно; обработка не обеспечивает exactly-once и не имеет устойчивой локальной дедупликации.

## HTTP и журналы

`GET /health` доступен без авторизации на порту `HTTP_PORT` (по умолчанию `:8080`). Ответ содержит `status`, `service`, `version` и `components`. Сейчас это базовый endpoint доступности процесса: поле Kafka в ответе выставляется как `UP` статически и не проверяет соединение. Поле database возвращает `DOWN` с пояснением, что база данных не настроена.

Основные сообщения журналов:

- `sending registration request` — отправка запроса;
- `successfully registered` — получен связанный ответ со статусом `REGISTERED`;
- `published HOLD recommendation` — рекомендация успешно опубликована, указаны тикер и номер последовательности;
- ошибки Kafka, разбора JSON и публикации записываются с уровнем ошибки.

Успешная обработка свечи сейчас не выводит цены OHLCV в журнал.

## Архитектура кода

`cmd/server` загружает конфигурацию, создает Kafka-клиент и use case, запускает HTTP endpoint и управляет остановкой процесса.

`internal/usecases` содержит сценарий регистрации, heartbeat и обработки свечей. Он работает через интерфейсы `KafkaPublisher` и `KafkaSubscriber` из `internal/ports`. `internal/adapters/kafka` реализует оба интерфейса с помощью franz-go. `internal/adapters/http` предоставляет health handler. `internal/domain` содержит конверт и модели событий. В коде нет отдельного слоя Momentum или реализации расчета технических индикаторов.

Основные технологии: Go 1.23, franz-go, `slog`, стандартный `net/http`, Docker и Docker Compose.

## Известные ограничения и следующие шаги

- Реализован только безопасный ответ `HOLD`; Momentum остается будущей функцией.
- Нет пользовательского интерфейса, базы данных, устойчивого состояния стратегии и локальной дедупликации.
- Ошибка чтения Kafka журналируется, но health endpoint ее не отражает.
- Цена и объем свечи не включены в текущий лог об успешной обработке.
- Для воспроизводимых экспериментов нужно согласовывать тему свечей, запуск и состояние платформенного портфеля с преподавателем.
- Интеграционная проверка зависит от доступности платформы, разрешений Kafka, выданных значений и наличия активного запуска свечей.
