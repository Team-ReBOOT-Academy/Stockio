# Stockio — сервис торговой стратегии

## 1. Название и назначение проекта

**Stockio** — серверный сервис торговой стратегии, предназначенный для учебной проверки алгоритма принятия торговых решений на основе исторических и поступающих рыночных данных.

Сервис является отдельным компонентом учебной системы. Он не подключается напрямую к реальной бирже и не совершает реальные торговые операции.

Основная задача сервиса — получить рыночные данные, обработать их выбранной торговой стратегией и сформировать торговый сигнал:

* `BUY` — купить;
* `SELL` — продать;
* `HOLD` — не совершать действие.

### Торговая идея

В качестве предварительно выбранной стратегии используется **Momentum**.

Стратегия оценивает изменение цены за заданное количество свечей:

```text
momentum = close[t] / close[t-N] - 1
```

Если изменение превышает положительный порог, стратегия формирует `BUY`.

Если изменение ниже отрицательного порога, формируется `SELL`.

Если изменение находится внутри заданного диапазона, формируется `HOLD`.

### Решаемая проблема

Проект позволяет отделить алгоритм торговой стратегии от преподавательской платформы и проверить его работу на стандартизированных рыночных данных.

Сервис должен предоставлять предсказуемый и воспроизводимый результат, который можно использовать в учебном соревновании или лабораторной работе.

### Цели

1. Реализовать самостоятельный сервер торговой стратегии.
2. Реализовать стратегию Momentum.
3. Обеспечить возможность запуска сервиса без среды разработки.
4. Подготовить сервис к взаимодействию с внешней учебной платформой.
5. Обеспечить базовую проверку состояния сервиса.

### Основные задачи

* создать серверное приложение на Go;
* реализовать конфигурацию через переменные окружения;
* реализовать стратегию Momentum;
* покрыть ключевую логику тестами;
* реализовать HTTP endpoint `/health`;
* обеспечить корректное завершение процесса;
* подготовить Docker-образ;
* описать запуск и назначение проекта в README.

### Ожидаемый результат

В результате должен быть получен запускаемый серверный сервис, который можно собрать одной командой, запустить локально или в контейнере и проверить через HTTP endpoint `/health`.

## 2. Границы проекта

### Входит в проект

В состав сервиса входят:

* серверное приложение на Go;
* конфигурация через переменные окружения;
* алгоритм торговой стратегии Momentum;
* обработка входных рыночных данных;
* формирование торгового решения `BUY`, `SELL` или `HOLD`;
* HTTP endpoint `/health`;
* автоматизированные тесты;
* Dockerfile;
* документация проекта.

### Не входит в проект

За пределами сервиса находятся:

* имитация реальной биржи;
* реальные торговые операции;
* управление банковскими или брокерскими счетами;
* пользовательский веб-интерфейс;
* самостоятельное получение котировок с биржи;
* система аутентификации конечных пользователей;
* расчёт реального финансового результата;
* управление преподавательской платформой;
* инфраструктура брокера сообщений, если она предоставляется внешней системой.

### Что контролирует сервис

Сервис отвечает за:

* собственную конфигурацию;
* состояние собственного процесса;
* реализацию торговой стратегии;
* обработку полученных рыночных данных;
* формирование результата работы стратегии.

Сервис не контролирует достоверность внешних рыночных данных, работу преподавательской платформы или доступность внешней инфраструктуры.

### Пользователи и внешние системы

Основные участники:

* разработчик;
* преподаватель или оператор учебной платформы;
* преподавательская платформа;
* внешняя система передачи рыночных данных;
* брокер сообщений, если он используется платформой.

## 3. Внешние системы и взаимодействия

### Преподавательская платформа

Преподавательская платформа является внешней системой, которая предоставляет сервису необходимые входные данные и может получать результаты работы стратегии.

Предполагаемое взаимодействие происходит через программный интерфейс или брокер сообщений.

На момент разработки первой версии точный контракт внешней платформы может быть неизвестен. Поэтому конкретные адреса серверов, названия топиков, формат авторизации и окончательные схемы сообщений считаются открытыми вопросами.

### Входные данные

Основным типом входных данных являются рыночные свечи.

Пример данных:

```json
{
  "runId": "run-42",
  "instrument": {
    "ticker": "SBER",
    "currency": "RUB",
    "lotSize": 10
  },
  "timeframe": "1m",
  "sequenceNumber": 51,
  "candleTime": "2026-09-24T08:15:00Z",
  "open": "281.10",
  "high": "281.80",
  "low": "280.90",
  "close": "281.40",
  "volume": 150000
}
```

### Выходные данные

Результатом работы стратегии является одно из решений:

```text
BUY
SELL
HOLD
```

В дальнейшем результат может передаваться преподавательской платформе через согласованный внешний интерфейс.

### Протоколы

Для локального управления и проверки состояния используется HTTP.

Для возможного взаимодействия с учебной платформой предполагается использование брокера сообщений.

Конкретный протокол и окончательный контракт внешнего взаимодействия должны быть подтверждены преподавательской платформой.

### Аутентификация

Секреты и параметры подключения к внешним системам не хранятся в исходном коде.

Они должны передаваться через переменные окружения или другой механизм конфигурации, предоставленный инфраструктурой учебной платформы.

### Возможные ошибки

Сервис должен учитывать:

* отсутствие входных данных;
* некорректный формат данных;
* недоступность внешней системы;
* ошибку подключения;
* некорректную конфигурацию;
* недостаточное количество свечей для расчёта стратегии;
* некорректные значения цены.

## 4. Состав решения

### Серверное приложение

**Назначение:** основной компонент проекта.

Отвечает за:

* запуск приложения;
* загрузку конфигурации;
* HTTP API;
* работу торговой стратегии;
* обработку ошибок;
* корректное завершение процесса.

### Стратегия Momentum

**Назначение:** вычисление торгового сигнала на основе изменения цены.

Отвечает только за алгоритм принятия решения и не занимается сетевым взаимодействием или хранением данных.

### HTTP API

**Назначение:** предоставление технического endpoint `/health`.

Endpoint позволяет определить, запущен ли сервис и отвечает ли он на HTTP-запросы.

### Внешняя учебная платформа

Является внешним компонентом.

Она предоставляет сервису необходимые данные и инфраструктуру для учебного сценария.

### База данных

В первой версии отдельная база данных не требуется.

Состояние стратегии может храниться в памяти процесса, если это необходимо для выполнения алгоритма.

### Брокер сообщений

Брокер сообщений не является частью локального сервиса в первой работе и рассматривается как внешняя инфраструктура при наличии соответствующего требования преподавательской платформы.
