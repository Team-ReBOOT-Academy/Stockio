# Stockio — сервис торговой стратегии

## 1. Название и назначение проекта

**Stockio** — серверный сервис торговой стратегии, предназначенный для учебной проверки алгоритма принятия торговых решений на основе исторических и поступающих рыночных данных.

Сервис является отдельным компонентом учебной системы. Он не подключается напрямую к реальной бирже и не совершает реальные торговые операции.

Основная задача сервиса — получить рыночные данные, обработать их выбранной торговой стратегией и сформировать торговый сигнал:

* `BUY` — купить;
* `SELL` — продать;
* `HOLD` — не совершать действие.

### Торговая идея

В качестве предварительно выбранной стратегии используется **Momentum**.

Стратегия оценивает изменение цены за заданное количество свечей:

```text
momentum = close[t] / close[t-N] - 1
```

Если изменение превышает положительный порог, стратегия формирует `BUY`.

Если изменение ниже отрицательного порога, формируется `SELL`.

Если изменение находится внутри заданного диапазона, формируется `HOLD`.

### Решаемая проблема

Проект позволяет отделить алгоритм торговой стратегии от преподавательской платформы и проверить его работу на стандартизированных рыночных данных.

Сервис должен предоставлять предсказуемый и воспроизводимый результат, который можно использовать в учебном соревновании или лабораторной работе.

### Цели

1. Реализовать самостоятельный сервер торговой стратегии.
2. Реализовать стратегию Momentum.
3. Обеспечить возможность запуска сервиса без среды разработки.
4. Подготовить сервис к взаимодействию с внешней учебной платформой.
5. Обеспечить базовую проверку состояния сервиса.

### Основные задачи

* создать серверное приложение на Go;
* реализовать конфигурацию через переменные окружения;
* реализовать стратегию Momentum;
* покрыть ключевую логику тестами;
* реализовать HTTP endpoint `/health`;
* обеспечить корректное завершение процесса;
* подготовить Docker-образ;
* описать запуск и назначение проекта в README.

### Ожидаемый результат

В результате должен быть получен запускаемый серверный сервис, который можно собрать одной командой, запустить локально или в контейнере и проверить через HTTP endpoint `/health`.

## 3. Внешние системы и взаимодействия

### Преподавательская платформа и Kafka

Платформа предоставляет защищенный Kafka-совместимый брокер, выданную тему свечей, секрет регистрации и стабильные идентификаторы. Сервис подключается к `omsu.7bits.it:9094` по `SASL_SSL` и `SCRAM-SHA-256`; логин/пароль Kafka аутентифицируют соединение, а `secretKey` в сообщениях связывает рекомендации с зарегистрированным аккаунтом. Точные учетные данные и топик свечей являются средовыми настройками, выдаваемыми преподавателем.

Сервис публикует `account.registration.request`, `account.service.heartbeat` и `strategy.recommendation.created`; читает `account.registration.result`, `strategy.recommendation.result` и `market.candle.closed` из выданного топика. Каждое сообщение использует общую оболочку с `eventId`, `eventType`, `schemaVersion`, `occurredAt`, `correlationId`, `causationId`, `producer` и `payload`. Сервис принимает только подтверждение регистрации, связанное с запросом по `causationId`, и не публикует рекомендации до статуса `REGISTERED`.

Kafka consumer group уникальна для аккаунта сервиса. Временные сбои брокера журналируются, клиент повторяет подключение, а HTTP health endpoint остается доступен. Ошибки авторизации и отклонение регистрации требуют исправления выданных настроек; отсутствующий/неверный топик или контракт — обращения к преподавателю. Ответы регистрации и рекомендаций фильтруются по собственным идентификаторам; секреты не записываются в журналы.

### Входные данные

Основным типом входных данных являются рыночные свечи.

Пример данных:

```json
{
  "runId": "run-42",
  "instrument": {
    "ticker": "SBER",
    "currency": "RUB",
    "lotSize": 10
  },
  "timeframe": "1m",
  "sequenceNumber": 51,
  "candleTime": "2026-09-24T08:15:00Z",
  "open": "281.10",
  "high": "281.80",
  "low": "280.90",
  "close": "281.40",
  "volume": 150000
}
```

### Выходные данные

Результатом работы стратегии является одно из решений:

```text
BUY
SELL
HOLD
```

В дальнейшем результат может передаваться преподавательской платформе через согласованный внешний интерфейс.

### Протоколы

Для локальной проверки состояния используется HTTP без авторизации (`GET /health`). Внешний обмен выполняется через Kafka поверх TLS и SCRAM-SHA-256. Контракт сообщений версии `1.0` приведен в документации учебной платформы; имя темы свечей и учетные данные остаются параметрами окружения.

### Аутентификация

Секреты и параметры подключения к внешним системам не хранятся в исходном коде.

Они передаются через переменные окружения: `KAFKA_USERNAME`, `KAFKA_PASSWORD`, `SECRET_KEY`, идентификаторы и темы. `.env` исключен из Git; `.env.example` содержит только имена настроек и безопасные примеры.

### Возможные ошибки

Сервис должен учитывать:

* отсутствие входных данных;
* некорректный формат данных;
* недоступность внешней системы;
* ошибку подключения;
* некорректную конфигурацию;
* недостаточное количество свечей для расчёта стратегии;
* некорректные значения цены.

### Допущения и открытые вопросы

* Kafka broker совместим с Kafka protocol и доступен из среды запуска по TLS.
* Преподаватель выдает актуальные Kafka credentials, `CANDLE_TOPIC`, `SECRET_KEY`, `ACCOUNT_ID`, `GROUP_ID`, `STRATEGY_ID` и уникальный `KAFKA_GROUP_ID`.
* Сервер платформы создает портфель по умолчанию при успешной регистрации; студент не задает его параметры.
* На первом этапе алгоритм безопасно отвечает `HOLD`; Momentum подключается после завершения базового потока обработки.
* Доставка после сбоя между публикацией рекомендации и commit Kafka не является атомарной. Для строгой идемпотентности в следующем этапе требуется устойчивый локальный журнал событий/исходящих сообщений.

## 4. Состав решения

### Серверное приложение

**Назначение:** основной компонент проекта.

Отвечает за:

* запуск приложения;
* загрузку конфигурации;
* HTTP API;
* работу торговой стратегии;
* обработку ошибок;
* корректное завершение процесса.

### Обработчик стратегии

На текущем этапе обработчик формирует `HOLD` для каждой свечи, чтобы проверить интеграцию и контракт. Momentum — следующий этап; этот алгоритм ещё не реализован. Когда он будет добавлен, компонент будет вычислять сигнал по данным и останется изолированным от сетевого взаимодействия.

### HTTP API

**Назначение:** предоставление технического endpoint `/health`.

Endpoint позволяет определить, запущен ли сервис и отвечает ли он на HTTP-запросы.

### Внешняя учебная платформа

Является внешним компонентом.

Она предоставляет сервису необходимые данные и инфраструктуру для учебного сценария.

### База данных

В первой версии отдельная база данных не требуется.

Состояние стратегии может храниться в памяти процесса, если это необходимо для выполнения алгоритма.

### Kafka adapter

**Назначение:** подключение к внешнему защищенному брокеру, регистрация сервиса, heartbeat, чтение событий, публикация рекомендаций и чтение результатов. Он не реализует торговую логику. Сбои обрабатываются повторными попытками; конкретный брокер и его учетные записи остаются вне поставки Stockio.

## 6. Инструменты и организация работы

* **Go 1.23** выбран для одного компилируемого серверного приложения с простым контейнерным запуском. Отдельный веб-фреймворк не нужен: единственный HTTP маршрут `/health` реализован стандартной библиотекой.
* **franz-go** используется как Kafka-клиент Go; он поддерживает TLS и SCRAM-SHA-256 без внешнего sidecar. Платформа предоставляет broker, темы и учетные данные, поэтому Stockio не разворачивает собственную Kafka.
* **Git** хранит исходный код, конфигурационный шаблон, документацию и схемы, чтобы изменения можно было проверять и возвращать.
* **Docker** дает повторяемую сборку и запуск без установленной среды Go; для локальной разработки доступны `go build` и `go run`.
* **Стандартная библиотека Go** предоставляет JSON, структурированные журналы `slog`, HTTP health endpoint и обработку сигналов завершения; это снижает число зависимостей каркаса.
* **Проверка** выполняется командами `go test ./...` и `go build ./...`. Интеграционная проверка Kafka зависит от выданных преподавателем доступов и темы.
* **Среда разработки** не влияет на сборку: проект собирается стандартными командами Go CLI. Внешний трекер задач должен содержать задачи на Kafka, регистрацию, прием свечи, `HOLD` и последующую Momentum работу; ссылку нельзя указать, поскольку адрес созданного проекта в исходных материалах отсутствует.

База данных, отдельный пользовательский интерфейс и дополнительный web framework для текущего объема не требуются.
